# The life of a system call

This document follows one system call, `write(1, "h", 1)` from xv6's
`echo`, through every step it takes in xv6-isor: the guest program, the
host Linux kernel, the sentry, and back. It then compares that path with
native Linux, a classic ptrace sandbox, User-Mode Linux and gVisor, and
measures what the detour costs.

You can watch the calls yourself with `-strace`:

```
$ printf 'echo hi\n' | ./xv6-isor -strace fs
...
[3 sh] exec("echo", 0x111f5f58) = 0
h[3 echo] write(1, 0x7ffe218abbd7, 1) = 1
i[3 echo] write(1, 0x7ffe218abbd7, 1) = 1
```

xv6's `printf` writes one character per call, which is why each letter
is its own `write`.

---

## The actors

| actor | what it is | where |
|---|---|---|
| guest | `echo`, a static x86-64 ELF making xv6 system calls | `user/echo.c`, `user/printf.c`, `user/usys.S` |
| host kernel | the real Linux kernel: syscall entry, ptrace | `arch/x86/entry/`, `include/linux/entry-common.h` |
| waiter goroutine | blocks in `wait4()` and forwards stop events | `sentry/kernel.go`, in `Run` |
| ptrace thread | the one goroutine, locked to an OS thread, that owns all sentry state | `sentry/kernel.go`, `sentry/syscall.go` |
| handler | `sysWrite`, xv6's `write` implemented in Go | `sentry/sysfile.go` |

```
 guest (echo)        host kernel             sentry: waiter      sentry: ptrace thread
     │                    │                        │                       │
     │ syscall (rax=16)   │                        │                       │
     ├───────────────────▶│ entry stop             │                       │
     │   (stopped)        ├──── wait4 returns ────▶│                       │
     │                    │                        ├── channel ───────────▶│
     │                    │◀────────── GET_SYSCALL_INFO, GETREGS ──────────┤
     │                    │◀────────── process_vm_readv (the "h") ─────────┤
     │                    │◀────────── write(1, "h") to the terminal ──────┤
     │                    │◀────────── SETREGS (orig_rax = -1), SYSCALL ───┤
     │                    │ skips the call         │                       │
     │                    │ exit stop              │                       │
     │                    ├──── wait4 returns ────▶├── channel ───────────▶│
     │                    │◀────────── GETREGS, SETREGS (rax = 1), SYSCALL ┤
     │◀───────────────────┤ sysret                 │                       │
     │ write returned 1   │                        │                       │
```

## Step 1: the guest asks

`echo` calls `printf(1, "%s", "hi")`. xv6's `printf` (`user/printf.c`)
calls `putc`, which calls `write(fd, &c, 1)`. `write` is a three-line
assembly stub generated by `user/usys.S`:

```asm
write:
    movl $16, %eax     # SYS_write in xv6's numbering (user/syscall.h)
    syscall
    ret
```

The arguments are already in place. The C calling convention put them in
`%rdi` (fd = 1), `%rsi` (the buffer) and `%rdx` (length 1), which is also
where the Linux system call convention expects them.

Two things make this a guest of xv6-isor rather than an ordinary Linux
program:

- **The number 16 is xv6's.** On Linux, 16 is `ioctl`. The program
  never runs on Linux's syscall table; the number only means something to
  the sentry.
- **It uses the 64-bit `syscall` instruction.** xv6 used `int $64`. The
  `syscall` instruction is what makes the host kernel's ptrace machinery
  report a 64-bit syscall stop.

## Step 2: the host kernel stops the guest

The `syscall` instruction switches the CPU to kernel mode at
`entry_SYSCALL_64` (`arch/x86/entry/entry_64.S`). That saves the user
registers into a `struct pt_regs` and calls `do_syscall_64()`
(`arch/x86/entry/syscall_64.c`). At this point the kernel has stored:

- `orig_ax = 16`: the system call number
- `ax = -ENOSYS`: the default return value

Before running anything, `do_syscall_64` calls the entry work. Because
the sentry traces this process with `PTRACE_SYSCALL`, the process has
syscall tracing enabled, and `syscall_trace_enter()`
(`include/linux/entry-common.h`) reports a **syscall-entry stop**. The
guest is put to sleep in the `TASK_TRACED` state, and its tracer, the
sentry, is notified.

seccomp filters run *after* the ptrace stop. The kernel source comment
says this is *"to catch any tracer changes"*. A tracer can rewrite a
system call before seccomp sees it.

## Step 3: the sentry wakes up

The sentry has two goroutines involved here (`sentry/kernel.go`):

- **The waiter goroutine** sits in `syscall.Wait4(-1, ..., WALL)`, the
  Linux `wait4` call. It returns with the guest's host pid and a status
  that says "stopped by `SIGTRAP | 0x80`". The `0x80` bit means it's a
  syscall stop, thanks to `PTRACE_O_TRACESYSGOOD`. The waiter sends the
  event on a channel.
- **The ptrace thread** receives it in the main loop (`case ev :=
  <-k.events`) and calls `handleWait`. Every ptrace request for a tracee
  must come from the thread that is its tracer, so all ptrace calls
  happen here.

Linux lets any thread of a process call `wait4` for the children of any
other thread in the same process. That is why the blocking `wait4` can
live on its own goroutine while all the ptrace requests stay on one
locked thread.

## Step 4: the sentry decodes the call

`syscallStop` (`sentry/syscall.go`):

1. **`PTRACE_GET_SYSCALL_INFO`** says whether this is an entry or an exit
   stop, and which ABI the guest used. If the guest used `int $0x80`, the
   32-bit entry, the process is killed: the 32-bit table numbers things
   differently, and the sentry's rewrites of `fork`, `exec` and `sbrk`
   would mean something else there.
2. **`PTRACE_GETREGS`** copies the guest's registers into a Go
   `syscall.PtraceRegs`.

`syscallEnter` then looks up `regs.Orig_rax` (16) in the sentry's own
table, which lists xv6's 21 calls plus `getprocs`, and finds
`sysWrite`. A number that isn't in the table gets `-1` and the message
`unknown sys call N`, exactly like xv6.

## Step 5: the sentry does the work

`sysWrite` (`sentry/sysfile.go`) is xv6's `sys_write` in Go:

1. **`argfd`** checks that fd 1 is open in the guest's file table. That
   table lives in the sentry (`Proc.ofile`), not in the host kernel. The
   guest has no host file descriptors at all.
2. **`copyIn`** reads the buffer out of the guest's memory with
   `process_vm_readv` (`sentry/mem.go`). xv6's kernel shares an address
   space with the process. The sentry is a different host process, so it
   has to copy across. The host kernel allows this because the sentry is
   the guest's tracer.
3. **fd 1 is the console**, a device file with major number 1, so the
   sentry calls `k.console.write(b)`. That is an ordinary Go
   `os.Stdout.Write`: a host `write(1, "h", 1)` made by the sentry, with
   the sentry's own arguments.

The handler returns `ret(1)`: an emulated call with result 1.

## Step 6: the sentry cancels the host system call

The guest is still stopped at the *entry* of system call 16. If the
sentry simply resumed it, the host kernel would run `ioctl`. So
`syscallEnter`:

1. sets `regs.Orig_rax = -1` and saves the result in `p.retval`
2. writes the registers back with `PTRACE_SETREGS`
3. resumes the guest with `PTRACE_SYSCALL`, asking to stop again at the
   syscall exit

Back in the host kernel, `do_syscall_64` now sees number `-1`, which is
not a valid system call. A comment in the kernel source explains what
happens:

> The special treatment of syscall number -1 is a historical bogosity
> as the original code used -1 to indicate syscall abort [...] The
> historic behavior is to keep the return value in regs->ax unmodified
> in that case, which means it's either the preset value -ENOSYS or a
> value which was written by a tracer.

So the host kernel runs nothing at all. This is the most important step
for security: **the host never executes a system call the guest chose**.

## Step 7: the exit stop and the return value

`syscall_exit_to_user_mode()` runs the exit work, which reports a
**syscall-exit stop**. The same path repeats: `wait4` → channel →
`GET_SYSCALL_INFO` (now "exit") → `GETREGS`. `syscallExit` sets
`regs.Rax = p.retval` (1), writes the registers back, and resumes the
guest.

The kernel returns to user mode with `sysret`. `%rax` holds 1, the stub's
`ret` returns it, and `write` returned 1. `echo` never knew it left its
own world.

The sentry could set `%rax` at the entry stop too, because the kernel
leaves it alone for number `-1`. It sets the value at the exit stop
because that also works for calls the host does run.

## Variations on the path

**Blocking calls** (`read` on a pipe or the console, `write` to a full
pipe, `wait`, `sleep`). The handler returns `blocked()` instead of a
value. The guest stays stopped at its entry stop, which costs nothing
while it waits. `k.async` runs the waiting part on a new goroutine, and
when it finishes it sends a closure back on `k.work`. The ptrace thread
then copies any data into the guest, sets `p.retval` and resumes it.
This is the user-space version of xv6's `sleep()`/`wakeup()`.

**Rewritten calls** (`fork`, `exec`, `sbrk`, `exit`). These need the host
to change the guest's process or memory, which the sentry can't do from
outside. So at the entry stop the sentry *replaces* the call with a host
call it builds itself: `fork` becomes `clone(CLONE_PARENT|SIGCHLD)`,
`exec` becomes `execve`, `sbrk` becomes `brk`, `exit` becomes
`exit_group`. It sets every argument register, and an exit hook fixes up
the result. See [processes.md](processes.md) and [memory.md](memory.md).

**Refused calls.** A Linux system call number (say 39, Linux's `getpid`)
is unknown to the table, so it gets `-1`. `int $0x80` kills the process.
`isortest` checks both.

## What the detour costs

Measured on the machine used to write this document, a cloud virtual
machine with 4 vCPUs. The programs were scratch code, not part of the
repository.

| what | time per call |
|---|---|
| native `getpid()` (a C loop calling `syscall(SYS_getpid)`) | about **100 ns** |
| the same loop under `strace -o /dev/null` (a minimal ptrace tracer) | about **44 µs** |
| xv6 `getpid()` under the sentry (20,000 calls, timed with `uptime()`) | about **125 µs** |

So intercepting a system call with ptrace is roughly 400 times slower
than making it, and the sentry is roughly three times slower than
`strace`. Virtual machines make context switches expensive, so expect
smaller numbers on bare metal, but similar ratios.

Where the time goes. Each guest system call costs, from the code:

| step | host system calls |
|---|---|
| entry stop | `wait4`, `PTRACE_GET_SYSCALL_INFO`, `PTRACE_GETREGS`, `PTRACE_SETREGS`, `PTRACE_SYSCALL` |
| the handler's own work | `getpid`: none. `write`: `process_vm_readv` + `write` |
| exit stop | `wait4`, `PTRACE_GET_SYSCALL_INFO`, `PTRACE_GETREGS`, `PTRACE_SETREGS`, `PTRACE_SYSCALL` |

That's about ten host system calls and four switches between the guest
and the sentry for every guest system call. On top of that, each stop is
handed from the waiter goroutine to the ptrace thread through a channel,
which usually means waking a second OS thread. That handoff, and the
extra `GET_SYSCALL_INFO`, are the main reasons the sentry is slower than
`strace`, which waits and traces from a single thread.

Ideas for making it faster are among the exercises below.

## How others take the same trip

| | how the call is caught | who runs it | host kernel sees the guest's call? | stops per call |
|---|---|---|---|---|
| **native Linux** | not caught | the host kernel | yes, it *is* the host's call | 0 |
| **classic ptrace sandbox** (e.g. a policy checker built on `strace`-like code) | `PTRACE_SYSCALL` | the host kernel, if the policy allows it | yes, approved calls run for real | 2 |
| **xv6-isor** | `PTRACE_SYSCALL` | the sentry (or a host call the sentry builds) | no: cancelled with `orig_rax = -1` | 2 |
| **User-Mode Linux** | traditionally `PTRACE_SYSEMU` | the UML kernel, itself a host process | no | 1: `SYSEMU` never runs the call, so there's no exit stop |
| **gVisor, systrap platform** (default) | seccomp `SECCOMP_RET_TRAP` turns the call into a `SIGSYS` signal inside a stub thread | the Sentry | no | no ptrace stops; the signal frame holding the thread's registers is on a stack shared with the Sentry |
| **gVisor, KVM platform** | the application runs in a hardware virtual machine; a syscall exits to the Sentry, acting as guest kernel | the Sentry | no | no ptrace; virtualization does the trap |

Some notes on the table:

- **A classic ptrace sandbox** is what gVisor's FAQ warns about:
  approved calls still reach the host's code, and another thread can
  change their arguments after the check. xv6-isor avoids both because
  the guest's call is never run and xv6 has no threads.
- **`PTRACE_SYSEMU`** would let xv6-isor skip the exit stop for
  emulated calls. It can't be used for everything, though: `SYSEMU`
  never runs the call, and xv6-isor needs the host to run its rewritten
  `clone`, `execve` and `brk`.
- **gVisor replaced its ptrace platform with systrap in mid-2023.** The
  trap happens inside the application's own stub threads, which avoids
  the tracer round trips measured above.

## Try it yourself

- **Watch every call:** `./xv6-isor -strace fs`. Each line is printed at
  the exit stop: `[pid name] call(args) = result`.
- **Compare with a real tracer:** run `strace -f` on any Linux program
  and compare the format.
- **Exercises:**
  1. **`PTRACE_SYSEMU`.** Why can't xv6-isor simply resume guests with
     `PTRACE_SYSEMU` and save the exit stop? Hint: you choose between
     `PTRACE_SYSCALL` and `PTRACE_SYSEMU` when you *resume*, before you
     know what the next call will be, and with `SYSEMU` the call is
     skipped even if you then decide the host should run it. What would
     `fork`, `exec` and `sbrk` have to become? (UML answers this by doing
     process and memory management itself.)
  2. **Remove the channel handoff.** Call `wait4` on the ptrace thread
     itself and measure `getpid` again. What happens to blocking calls,
     whose completions currently arrive on `k.work`, and how could they
     wake the loop instead?
  3. **Make fewer calls.** xv6's `printf` makes one `write` per
     character. Change it to build the output in a buffer and write once.
     How much faster does `ls` run under the sentry, and why does it
     barely matter on real xv6?
